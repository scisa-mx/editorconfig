# Manejo de subdominios

## Propósito

Definir el patrón canónico de subdominios para todos los sitios que SCISA levanta — servicios centrales, servicios por cliente y ambientes — para garantizar consistencia en registros DNS, certificados y comunicación con clientes.

---

## Dominios raíz

| Dominio | Producto |
|---|---|
| `scisa.com.mx` | SIGLO CD |
| `scisa-pld.com` | SIGLO PLD |

El dominio sigue al producto. Un cliente de SIGLO CD nunca aparece en `scisa-pld.com` y viceversa.

---

## Patrón canónico

### Servicios centrales (sin nivel de cliente)

```
<servicio>.<dominio>
```

Ejemplos:
- `api.scisa.com.mx`
- `admin.scisa-pld.com`

### Servicios por cliente

```
<servicio>.<cliente>.<dominio>
```

Ejemplos:
- `app.bancrea.scisa.com.mx`
- `api.actinver.scisa-pld.com`

---

## Ambientes

Todos los ambientes exponen subdominio público con certificado TLS válido.

| Ambiente | Patrón | Ejemplo |
|---|---|---|
| Producción | `<servicio>.<cliente>.<dominio>` | `app.bancrea.scisa.com.mx` |
| QA | `<servicio>.<cliente>.qa.<dominio>` | `app.bancrea.qa.scisa.com.mx` |
| Dev (compartido) | `<servicio>.dev.<dominio>` | `app.dev.scisa.com.mx` |

**Reglas:**
- `dev` es compartido entre todos los equipos — no tiene nivel de cliente.
- `qa` es el ambiente que el cliente usa para validar antes de producción.
- El slug del cliente no cambia entre ambientes — solo cambia el nivel de ambiente en la jerarquía.
- Los servicios centrales siguen el mismo patrón de ambiente: `<servicio>.qa.<dominio>`, `<servicio>.dev.<dominio>`.

---

## Reglas de nomenclatura de slugs

Aplica tanto al slug de cliente como al slug de servicio.

| Regla | Correcto | Incorrecto |
|---|---|---|
| Solo minúsculas | `bancrea` | `BANCREA`, `Bancrea` |
| Solo alfanumérico + guión | `api-pld` | `api_pld`, `apiPld` |
| Sin espacios ni caracteres especiales | `actinver` | `actinver!`, `actinver.pld` |

## Proceso de solicitud

### Paso 1 — Aprobación del Lead Técnico

Antes de contactar a Soporte, el solicitante obtiene aprobación explícita del Lead Técnico. El Lead valida que:
- El nombre sigue el patrón canónico de este documento
- El ambiente corresponde al uso declarado
- El registro no duplica uno ya existente

### Paso 2 — Solicitud a Soporte Técnico

Enviar email a `soporte@scisa.com.mx` con la siguiente información:

```
Asunto: Alta de registro DNS — <hostname completo>

Hostname:         app.bancrea.qa.scisa.com.mx
Tipo de registro: A   (o CNAME si apunta a otro host)
Valor:            <IP o hostname destino>
TTL:              default
Aprobó:           <nombre del Lead Técnico>
```

Soporte Técnico realiza únicamente el registro DNS. El certificado TLS es responsabilidad del solicitante.

### Paso 3 — Generación del certificado

Una vez que el registro DNS está activo, generar el certificado con WinACME:

```
wacs.exe --target manual --host app.bancrea.qa.scisa.com.mx
```

Antes de dar el alta como completada, verificar que la renovación automática esté configurada.

---

## Ciclo de vida

### Alta

El Lead Técnico aprueba y el solicitante ejecuta los pasos anteriores.

### Baja inmediata

Cuando un cliente termina o un ambiente se desactiva, el Lead Técnico envía email a `soporte@scisa.com.mx` solicitando la eliminación del registro. El solicitante revoca o deja vencer el certificado TLS asociado.

### Auditoría trimestral

Cada trimestre el Lead Técnico audita los registros DNS activos contra los clientes y ambientes vigentes. Los registros sin uso activo se dan de baja.
